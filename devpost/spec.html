HoneKit

Five services, one bag. A curriculum, a progress ledger, a crew read, and a leader who can turn a meeting brief into a roster.

status: approved .NET 10 · Aspire 13.6 React + Vite Docker Compose SQLite per service 5 services + frontend

$ aspire deploy → builds images · generates compose · http://localhost:8080

01How it fits together

Each service owns one kind of data and lets the others ask. Only one of them ever calls a model.

The bag is derived, not pushed. Roster & Bags reads Progress and works out which tools exist; nothing has to be synchronised, so the drop can’t drift out of date.
One model, generated output. The AppHost declares all of this — services, references, volumes, endpoints — and aspire publish emits the Compose file. The YAML is committed so it can be read and deployed without the CLI, but it is never hand-edited. That is Microsoft’s stated guidance, and it removes the second source of truth entirely.

06The dials we fixed

Carried from the PRD’s open questions into concrete numbers.

0.70Frame overlap (IoU) at or above this counts as correct — and the score screen shows the measured overlap.
80%Of cards correct on first attempt for the deck to pass. Below it, the result still closes cleanly.
90%First-try correct, with at most 2 retries, and the tool arrives honed. Otherwise plain.
+2Cards before a wrong answer returns in the same session. Right answers resurface in 3 days; wrong ones in 10 minutes.

07When it breaks

Eight realistic failures, each with a chosen behaviour rather than an apology.

FailureWhat the leader or member sees
No AI key, provider down“Reading is unavailable” plus the manual requirement form, prefilled with the extracted text.
Model invents a skillValidation rejects it, one retry with the error attached, then the form with the bad items highlighted.
PDF is a scan“This looks like a scan — paste the text,” textarea focused.
A service is downThat page shows a labelled partial state; the rest of the app keeps working.
Model takes > 30sCancelled with a plain message and the manual path offered.
Cold compose upHealth checks gate the frontend; the app shows “connecting” for a few seconds, not a broken page.
First boot or wiped volumeThe service seeds itself and logs it; the app opens on a fresh demo rather than an empty shell.
Nothing earned yetEmpty bag is an invitation, not an error. Same for no plans, no requirements.

08Build order, and why it’s shaped this way

Contracts first, then services that can be built in parallel, then the two leader surfaces. This is the orchestration practice: eight packages an agent can own outright.

  1. Contracts + AppHost + compose environmentFive services that start, appear in the dashboard, and survive a first aspire publish. Containerising later is a retrofit.
  2. Content + ProgressParallel-safe. Grading, scheduling, pass and honed rules land here with unit tests.
  3. Roster & BagsThe aggregate read, the worn bag, personalisation. Can start against contracts.
  4. Frontend, member sideThe framing canvas cannot wait for anything else — pointer events and normalised coordinates.
  5. RequirementsFixture parser first, then the live provider. The fallback form is a feature, not a stub.
  6. RecommendationsPure logic over contracts; the best slice to run in parallel with the frontend.
  7. Frontend, leader plan sideUpload, edit, strategy, override, save.
  8. Polish passArt, motion, responsive, empty states, then the demo script.
